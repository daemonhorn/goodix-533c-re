# PSK provisioning algorithm — decompiled logic analysis

Source material: `findings/ghidra-psk-decompile.md` (auto-generated by
`ghidra_scripts/FindPskFunctions.java`, decompiling every function that
references the `"1.seal psk by sgx"` / `"2.process encrypted psk"` /
`"3.write psk to mcu"` / `"../common/sgx/PskUnify.c"` / `GfSealData` /
`GfUnsealData` strings, plus one level of caller context). This report
reconstructs what that pseudocode actually does, cross-checked line by line;
it does not introduce new static analysis beyond reading that file. Tone and
confidence labeling follow `SUMMARY.md`/`phase2-psk-write-attempts.md`.

## 0. Two independent code paths exist, not one

The decompile file turns out to contain **two structurally parallel but
separately-implemented PSK-provisioning sequences**, apparently for two
different companion-MCU families bundled in the same `.so` (consistent with
Phase 1's finding that this binary bundles config data for multiple chip
families):

| | "Geneva" path | "Stm32" path |
|---|---|---|
| Source tags | `../common/sgx/PskUnify.c`, `../mcu/Geneva/Geneva.c` | `../mcu/Stm32/Stm32.c` |
| Top-level function | `ProcessPsk` (`FUN_0011d5d0`) | `StmMcuProcessPsk` (`FUN_00124990`, with `ProductionWriteKey`/`ProductionWriteMcu`/`GFFindAPPOrIAP`/`CleanPskCache` inlined into the same binary function) |
| Write step | `PresetPskWriteKey` (`FUN_00113620`) | inlined `ProductionWriteKey`/`ProductionWriteMcu` block inside `FUN_00124990` |
| MCU opcode used | not directly visible (see §3) | **`0xe0`** — confirmed identical to `COMMAND_PRESET_PSK_WRITE_R` in `goodix.py` |

**Which of these two paths PID `0x533c` actually uses is not determined by
this decompile file.** Nothing in the traced functions branches on USB PID;
selection is presumably driven by the same runtime chip-ID/OTP dispatch that
Phase 1 already flagged as undetermined for `DEVICE_CONFIG`. This is the
single biggest open question left after this pass — see §5.

## 1. What `GeneratePsk` / `PresetPskWriteKey` (Geneva path) actually does

### 1a. Randomness source

Confirmed directly in code (`ghidra-psk-decompile.md:54,68`):

```c
pvVar4 = (void *)FUN_0010b960(0x20);           // malloc 32 bytes
...
iVar2 = FUN_0010b180("/dev/urandom",pvVar4,0x20);  // read 32 bytes from /dev/urandom
```

32 bytes of real OS randomness is the seed for everything downstream. This
matches what the calling agent already spotted before requesting this
analysis.

### 1b. The "XOR-mixing" loops are, per plain C semantics, a flat XOR against a fixed 32-byte table

Four back-to-back `while` loops each process 8 bytes of the 32-byte random
buffer, e.g. (`ghidra-psk-decompile.md:72-91`):

```c
bVar12 = 0xd5; bVar13 = 0x58; bVar14 = 0xd9; bVar11 = 0x3a;
lVar5 = 0; pbVar9 = local_88; pbVar10 = &DAT_001db5c1;
while( true ) {
  *pbVar9 = bVar11 ^ bVar14;                              // dead store
  *pbVar9 = bVar12 ^ *(byte *)((long)pvVar4 + lVar5);      // dead store
  *pbVar9 = bVar13 ^ *(byte *)((long)pvVar4 + lVar5);      // <- the value that survives
  if (lVar5 + 1 == 8) break;
  bVar14 = (&DAT_001db5a1)[lVar5]; bVar11 = *pbVar10; bVar12 = pbVar10[8]; bVar13 = pbVar10[0x10];
  lVar5 = lVar5 + 1; pbVar9 = pbVar9 + 1; pbVar10 = pbVar10 + 1;
}
```

Each loop body writes to the **same memory location `*pbVar9` three times**
in a row with no intervening read; under standard C assignment semantics
only the last write (`bVar13 ^ pvVar4[lVar5]`) has any observable effect —
the first two XORs are dead stores. Applied consistently across all four
loops, this means:

> **`GeneratePsk`'s "mixing" step is functionally a byte-for-byte XOR of the
> 32 random bytes against a fixed 32-byte keystream table**, whose bytes are
> the literal constants (`0x58, 0x9d, 0x6b, 0xf, ...` — one seed byte per
> loop) followed by successive bytes pulled from four `.rodata` tables at
> `DAT_001db5a1`, `DAT_001db5c1`, and three `UNK_001db5xx` addresses.

Confidence: **high for the "reduces to plain XOR" reading**, since it
follows directly from unremarkable, side-effect-free C assignment semantics
in the pseudocode as transcribed. Residual uncertainty: this is Ghidra's
*decompiled* rendering, not raw disassembly — it's conceivable (though
atypical for this pattern) that this reflects a masked/predicated SIMD
write Ghidra split into sequential scalar statements it couldn't fully
collapse. I did not go back to disassembly to rule that out; if it matters,
re-checking the raw `.text` at this address (documented in
`ghidra-psk-decompile.md` around `FUN_00113620`, roughly VA `0x113620`+0x160)
would settle it definitively.

**What I do NOT have**: the literal byte contents of the `DAT_001db5a1` /
`DAT_001db5c1` / `UNK_001db559/561/569/579/581/589` tables — the generating
script only recorded symbol names, not bytes. So while the *shape* of the
transform (raw-random XOR fixed-table) is established, the actual 32-byte
keystream is not yet extracted. This is different in kind from the 96-byte
`PSK_WHITE_BOX` candidate found in Phase 1 (`psk-whitebox.md`) — **do not
conflate the two**; nothing here confirms or denies that Phase-1 candidate.

### 1c. The masked random value is then hashed

```c
free(pvVar4);
uVar6 = FUN_001cb850(local_88,0x20,local_68);   // 32B in -> 32B out
```

`FUN_001cb850` is called elsewhere in this file with the same 32-byte-in/
32-byte-out shape to compute a value later compared via `memcmp` against a
hash read back from the MCU (`FUN_00112b10`/`PresetPskIsVaildG`,
`ghidra-psk-decompile.md:821-836`, comment: `"4.verify hash of local and mcu"`).
It is also used to hash a 0x44-byte structured buffer (`__ptr` built as
`[1-byte len][0x20 data][1-byte len]`-ish TLV) into a "raw_pmk" in
`CalculatePmk`/`FUN_00112f60` (`ghidra-psk-decompile.md:1204-1221`).

**Inference (not confirmed by reading `FUN_001cb850` itself, which is not in
this decompile file): this is very likely a fixed-size cryptographic hash
(32-byte digest strongly suggests SHA-256), used both as a PSK-derivation
step and as a local/MCU verification hash.** I label this "inferred from
call shape," not "confirmed" — the function body would need to be pulled to
be sure it isn't, e.g., a proprietary non-standard 32-byte digest.

Similarly, `FUN_001cba10` (called with 64-byte key + 64-byte
sequentially-numbered input block `0x01..0x40` in `GetPmkHmac`/`FUN_00113fc0`,
and again in `PresetPskIsValidR`/`FUN_00113150` to compute something
compared against `"read hmac of pmk"`) has the classic shape of an
**HMAC construction** (64-byte key/block size = HMAC-SHA256 block size).
Same caveat: inferred from usage pattern, body not present in this file.

### 1d. Where the derivation output *actually goes* is ambiguous in this trace

After the XOR+hash sequence, `PresetPskWriteKey` logs `"1.seal psk by sgx"`
and calls (`ghidra-psk-decompile.md:173-174`):

```c
*__ptr = 0x7f8bb010002;   // low 32 bits = 0xbb010002 (TLV command tag)
uVar6 = FUN_00112a70(param_4,local_a8,0x20,__ptr + 1,(long)__ptr + 4);
```

`FUN_00112a70` **is** `GfSealData` (confirmed — it logs its own name):

```c
uint FUN_00112a70(long param_1,long param_2,undefined8 param_3,long param_4,long param_5)
{
  if (param_1 == 0) { uVar1 = 0x97; }
  else if ((param_4 != 0 && param_5 != 0) && (param_2 != 0)) {
    uVar1 = FUN_001d8d60(*(undefined8 *)(param_1 + 0x178));
    return uVar1;
  }
  ...
  FUN_0010c940(...,"GfSealData",uVar1,0,"valide parameter");
  return 0xffffffff;
}
```

Two things worth flagging honestly:

1. **`GfSealData` itself is a thin wrapper.** The real work happens in
   `FUN_001d8d60`, reached through a value stored at offset `0x178` of the
   device-context struct (`param_1`) — this reads like a function-pointer or
   opaque-handle dispatch, not inline crypto. `FUN_001d8d60`'s body is *not*
   in this decompile file.
2. **The decompiled call site only shows one argument being forwarded**
   (`*(undefined8 *)(param_1 + 0x178)`) even though `GfSealData` itself
   received five parameters including buffer/length/output pointers that
   would need to reach the real implementation somehow. This is most
   plausibly a Ghidra signature-inference artifact (it under-resolved
   `FUN_001d8d60`'s true parameter count) rather than evidence that the seal
   call genuinely discards its buffer arguments — but I can't rule out the
   less likely alternative from this file alone.
3. Consequently, whether the buffer actually sealed (`local_a8`, passed as
   `GfSealData`'s `param_2`) is the XOR+hash output from §1c, or the *raw*
   32 bytes of `/dev/urandom`, is **not cleanly traceable in this excerpt** —
   `local_a8` is zero-initialized at function entry and I can't find an
   explicit assignment into it before this call in the transcribed
   pseudocode. Section 2 below (the complete, unambiguous Stm32 path) shows
   the analogous step uses the *raw* random bytes as input to both
   downstream transforms, which is circumstantial evidence the Geneva path
   likely does the same and that this is a decompiler stack-slot-labeling
   gap rather than a real "seal nothing" bug — but this is an inference, not
   a confirmed reading. **Flagged as a concrete unresolved item for §5.**

After the seal step, a second TLV block is built with `FUN_001cd700`
(same function reused by the Stm32 path, see §2) tagged `0xbb010003`, and
the two TLV blocks (`0xbb010002` header+payload, then `0xbb010003`
header+payload) are concatenated into one buffer via straight `memcpy`s
(`ghidra-psk-decompile.md:187-191`).

### 1e. Platform gating — and the send-or-not branch

The combined buffer is only actually transmitted if a platform-identifier
string (`param_1` to `PresetPskWriteKey`) matches `"GM168"` or `"GM168SEC"`:

```c
if ((iVar2 == 0) || (iVar2 = memcmp(param_1,"GM168SEC",uVar6), iVar2 == 0)) {
  FUN_0010c940(...,"platform is geneva");
  uVar3 = FUN_0011ff90(pvVar4,uVar3,param_4);   // <- the actual send
  ...
}
else {
  iVar2 = memcmp(param_1,"RTSEC",uVar6);
  if (iVar2 == 0) {
    FUN_0010c940(...,"platform is realtek");   // <- logged, but NO send call follows
  }
}
```

**Confirmed from the code as transcribed: for the `"RTSEC"` platform string
— and for any string that matches neither `"GM168"`/`"GM168SEC"` nor
`"RTSEC"` — this function never calls a send/transmit function at all**,
yet still returns a "success" code from the earlier seal/process steps.
`FUN_0011ff90` is the real send call for the Geneva/GM168 branch; its body
is not in this decompile file, so its wire framing (opcode, headers) is
unconfirmed from this pass — unlike the Stm32 path (§2), where the send
call's opcode is directly visible.

## 2. The Stm32 path (`ProductionWriteKey`/`ProductionWriteMcu`, inlined into `FUN_00124990`) — fully traceable buffer layout

This path is unambiguous end-to-end and is the strongest evidence in the
whole file, because every step's inputs/outputs are visible in one
function body.

```c
iVar5 = FUN_0010b180("/dev/urandom",local_168,0x20);      // 0. raw 32-byte random PSK, NO XOR masking here
...
uVar8 = FUN_001cb1f0(0,local_c8,local_a8,local_168,0x20,__ptr_00,local_268);  // 1. "seal"
...  // log: "seal psk, ret 0x%x length before %d, length after:%d", 0x20 -> local_268[0]
*__ptr_01 = 0x7f4bb010003;
uVar2 = FUN_001cd700(local_168,0x20,__ptr_01 + 1,(long)__ptr_01 + 4);        // 2. "process"
...
__ptr_02[1] = iVar5;               // len field = sealed_len + 0x14
*__ptr_02 = 0xbb010002;
memcpy(__ptr_02 + 3,__ptr_00,__n);                      // sealed blob payload
puVar18 = (undefined8 *)((long)__ptr_02 + __n + 0xc);
*puVar18 = *__ptr; puVar18[1] = __ptr[1]; *(undefined4*)(puVar18+2) = *(undefined4*)(__ptr+2); // 20B entropy block
memcpy((void *)((long)__ptr_02 + __n + 0x20),__ptr_01,(ulong)uVar2 + 0xc);  // processed blob (0xbb010003)
...
iVar5 = FUN_00115ed0(uVar10,0xe0,__ptr_02,uVar7 & 0xffffffff,&local_272,&local_26c,uVar6,uVar4);
```

Confirmed points:

- **Step 0 uses the raw 32 `/dev/urandom` bytes directly** as input to
  *both* downstream transforms — no XOR-table masking happens on this
  path (that masking is unique to the Geneva `GeneratePsk` code in §1).
- **Step 1 (`FUN_001cb1f0`, "seal")**: input is the raw 32-byte PSK, output
  is a longer buffer (`local_268[0]` bytes, i.e. "length after" > "length
  before" per the log string) — consistent with an IV-prepended or
  padded block-cipher ciphertext. The failure branch for this exact call is
  logged as `"SecAes256CbcNopad failed with error code:0x%x."`
  (`ghidra-psk-decompile.md:634-635`) and a sibling failure path is logged
  `"[FAILED] WhiteBox encryption failed with 0x%x."` — **naming evidence
  (not a decompiled algorithm body) that this step is AES-256-CBC,
  no-padding, using some form of "white-box" key material.** This is an
  inference from log strings, not from reading `FUN_001cb1f0`'s body (not
  in this file).
- **Step 2 (`FUN_001cd700`, "process")**: also takes the *raw* 32-byte PSK
  as input (`local_168`, not the step-1 ciphertext) and produces a second,
  independent TLV payload tagged `0xbb010003`. **This is the single most
  actionable finding for the project's open question**: `0xbb010003` is
  exactly the `flags` value already tried against real hardware with the
  flat `PSK_WHITE_BOX` blob in Phase 2 (both attempts, rejected with
  `message[0]==0x01`). This code shows `0xbb010003`'s payload is expected to
  be **the output of `FUN_001cd700` applied to a genuinely random 32-byte
  value**, not a static 96-byte constant — a concrete, code-grounded
  explanation for why the flat blob was rejected, going beyond the
  circumstantial "seal psk by sgx" naming that motivated this
  investigation in the first place.
- **The final send call passes opcode `0xe0`** — confirmed identical to
  `COMMAND_PRESET_PSK_WRITE_R` in `vendor/goodix-fp-dump/goodix.py`. This is
  the strongest cross-reference in the whole file between this vendor
  C code and the already-reverse-engineered Python wire protocol.
- **Final wire buffer layout** (assembled, all offsets read directly from
  the arithmetic in the code):
  ```
  [4B  0xbb010002 LE]  [4B length = sealed_len+0x14]  [4B reserved=0]
  [sealed_len bytes: FUN_001cb1f0 output ("sealed"/AES output of raw PSK)]
  [20 bytes: entropy/nonce block from FUN_00123a60]
  [4B  0xbb010003 LE]  [4B length = processed_len]
  [processed_len(+4 slop) bytes: FUN_001cd700 output (second, independent transform of the same raw PSK)]
  ```
  sent as the payload to opcode `0xe0`.

This is a materially different, multi-part, TLV-structured payload — not a
flat 96-byte blob — and it embeds a **fresh 32 bytes of real randomness
every time**, meaning **there is no static constant that could ever work**
for this path; a correct implementation must generate new randomness and
run it through whatever `FUN_001cb1f0` and `FUN_001cd700` actually compute.

## 3. "seal by sgx" / `GfSealData` / `GfUnsealData` — is this real SGX?

**Verdict: (b) — a portable, software-only mechanism that borrows SGX
naming/terminology, not (c) real Intel SGX enclave hardware.**

Evidence:

- `GfSealData` (`FUN_00112a70`) and `GfUnsealData` (`FUN_001129f0`) are both
  short, ordinary C wrapper functions with standard calling conventions —
  no enclave-entry trampolines, no `ENCLU`/`EENTER` instructions, no calls
  to Intel SGX SDK symbols (`sgx_create_enclave`, `sgx_ecall`,
  `sgx_uae_service`, etc.) appear anywhere in this decompile file.
- `SUMMARY.md` §2 already established (independently, from
  `dynamic-symbols.txt`/`dynamic-deps.txt`) that this `.so`'s only linked
  dependencies are `libfprint-2-tod.so.1`, `libpthread`, `libm`, `librt`,
  `libc` — **no Intel SGX PSW/URTS library is linked at all.** Real SGX
  enclave calls are impossible without that linkage.
- Both wrappers dispatch through a value at offset `0x178` of a
  device-context struct into `FUN_001d8d60`/`FUN_001d9340` — consistent
  with an internal abstraction layer (possibly supporting multiple
  "secure" backends across different Goodix product lines, of which only
  this software one is actually linked in for this `.so`) rather than a
  literal enclave boundary.

Confidence: **high** for "not real SGX hardware, given this binary." The
one gap is that `FUN_001d8d60`/`FUN_001d9340` themselves are not in this
decompile file, so I can't directly confirm what they compute (AES? a
proprietary white-box scheme? something else) — only that whatever it is,
it executes as ordinary userspace code linked against libc, not real SGX.
This matches hypothesis (b) as stated in the task, not (a) dead code (it is
clearly on the live call path from `ProcessPsk`/`libgxfp_enroll_finger`) nor
(c) real enclave hardware.

## 4. Literal constants found vs. dynamically generated values

| Value | Static constant or dynamic? | Notes |
|---|---|---|
| 32-byte `/dev/urandom` read (both paths) | **Dynamic**, freshly generated per call | Confirmed, `FUN_0010b180("/dev/urandom", buf, 0x20)` |
| Geneva-path XOR keystream (§1b) | **Static** table in `.rodata`, but **only referenced by symbol name here** (`DAT_001db5a1`, `DAT_001db5c1`, `UNK_001db559/561/569/579/581/589`) — literal byte *contents* not extracted in this pass. 16 literal seed bytes were captured directly from the C source: `0x58,0x9d,0x6b,0x0f` (the four loops' effective initial XOR bytes) plus 12 more (`0xd5,0xd9,0x3a / 0xb5,0xe1,0x7d / 0xc7,0xeb,0xd5 / 0xbe,0x92,0x13`) that are provably dead stores under plain C semantics — see §1b caveat | Do not treat this as a candidate replacement for `PSK_WHITE_BOX`; it's a keystream applied to *fresh* randomness every call, structurally incapable of being a static PSK by itself |
| 20-byte "entropy" block (Stm32 path, `FUN_00123a60`) | Likely **dynamic** ("generate entropy" log tag) but its internals aren't shown | Unconfirmed whether it's pure `/dev/urandom` or partially derived from device state |
| TLV command tags `0xbb010002` / `0xbb010003` | **Static** | Directly confirmed as 32-bit literal immediates at multiple call sites in both paths; `0xbb010003` matches the exact flags value already tried (and rejected) on real hardware in Phase 2 |
| Opcode `0xe0` passed to `FUN_00115ed0` | **Static** | Confirmed identical to `COMMAND_PRESET_PSK_WRITE_R` in `goodix.py` |
| `PSK_WHITE_BOX` (Phase 1's 96-byte candidate at file offset `0xf1bab`) | Not referenced anywhere in this decompile file | This pass found **no code cross-reference** tying that address to any function shown here, consistent with — but not proof of — Phase 1's own finding that it was never code-cross-referenced either |

No new 96-byte-or-similar static blob was found in this pass. The two
"seal"/"process" functions central to this analysis (`FUN_001cb1f0`,
`FUN_001cd700`) both take a **dynamically generated** 32-byte value as
input on the Stm32 path — reinforcing that this chip's provisioning is
fundamentally incompatible with any flat static-blob approach, regardless
of which 96 bytes are chosen.

## 5. Is this replicable in pure Python without real SGX hardware?

**Yes, in principle — §3 rules out any hard SGX-hardware dependency — but
not yet in practice**, because the actual cryptographic content of the two
load-bearing transforms (`FUN_001cb1f0` "seal"/AES step, `FUN_001cd700`
"process" step) is not in this decompile file. Confidence in the overall
"no real SGX required" conclusion: **high**. Confidence that the algorithm
is *fully specified* by what's been decompiled so far: **low** — this pass
mapped the control flow and buffer layout precisely, but the byte-level
transforms inside the two key functions remain black boxes.

### What's solid enough to act on already

- The MCU write opcode (`0xe0`) and the two-TLV, `0xbb010002`+`0xbb010003`
  buffer structure (Stm32 path) — could be scaffolded into Python now.
- Both transforms consume **freshly generated 32-byte randomness**, not a
  static key — any Python implementation must generate new randomness per
  attempt, matching neither of the Phase-2 static-blob attempts.
- No SGX hardware/driver is required to reimplement this in userspace.

### What's still missing before a working Python implementation is possible

## For the calling session

Confirmed: `0xe0` (Stm32 path's send opcode) matches
`COMMAND_PRESET_PSK_WRITE_R`, and the payload is a two-part TLV buffer
(`0xbb010002` = "sealed"/AES-like output, `0xbb010003` = "processed"
output) built from a **fresh 32-byte `/dev/urandom` value every time** —
never a static blob. This directly explains why the flat 96-byte
`PSK_WHITE_BOX` was rejected with `0xbb010003` in Phase 2: that opcode's
payload is supposed to be the output of an unresolved transform
(`FUN_001cd700`) applied to live randomness, not a constant. "Seal by sgx"
is confirmed **not** real Intel SGX hardware (no SGX libs linked, no
enclave instructions) — just borrowed naming around ordinary AES/hash-style
code, so this is replicable in pure Python in principle. However, the two
load-bearing transforms (`FUN_001cb1f0` "seal" and `FUN_001cd700`
"process") are still black boxes — their bodies aren't in the current
decompile file. Also unresolved: whether `0x533c` uses this "Stm32" path or
the parallel, less-complete "Geneva" path traced here. Recommended next
step: decompile `FUN_001cd700` and `FUN_001cb1f0` specifically (highest
value), and if possible, get a live debug-log capture from real hardware to
settle the Geneva-vs-Stm32 question before investing in more static
analysis.
